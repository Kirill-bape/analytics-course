## Зачем отдельное хранилище

У компании десятки систем: сайт и приложение пишут заказы в свою базу, CRM хранит клиентов, склад — остатки, бухгалтерия — платежи, рекламные кабинеты — расходы. Каждая система хороша для своей работы, но аналитику нужен ответ на вопрос, который касается всех сразу: «Какая выручка с клиентов из рекламы ВКонтакте с учётом возвратов и затрат на доставку?»

**Хранилище данных** (DWH, data warehouse) — отдельная база, куда данные из всех систем регулярно собираются, очищаются, приводятся к единым определениям и хранятся с историей. Именно с хранилищем работают аналитики и BI-системы.

## OLTP и OLAP

| | OLTP — рабочие базы систем | OLAP — аналитическое хранилище |
|---|---|---|
| задача | быстро записать и прочитать одну запись: создать заказ, сменить статус | посчитать итоги по миллионам строк |
| запросы | короткие, тысячи в секунду | тяжёлые, с группировками и `JOIN` |
| данные | текущее состояние | история за годы |
| структура | нормализованная, много связанных таблиц | удобная для анализа, часто денормализованная |
| хранение | по строкам (PostgreSQL, MySQL) | часто по столбцам (ClickHouse, Greenplum, BigQuery) |

Почему не считать отчёты прямо в рабочей базе сайта? Тяжёлый аналитический запрос может её замедлить, и покупатели не смогут оформить заказ. А ещё там нет истории: когда статус заказа меняется, старое значение просто перезаписывается.

## Слои хранилища

Данные проходят несколько слоёв, и у каждого своя роль:

1. **Сырой слой** (raw, staging, ODS) — копия данных из источников «как есть», с отметкой времени загрузки. Если дальше что-то пошло не так, всегда можно пересчитать из сырья.
2. **Детальный слой** (DDS, core) — очищенные, связанные между собой данные с единой моделью: клиенты, заказы, товары. Здесь разбираются дубли, приводятся форматы, ведётся история изменений.
3. **Витрины** (data marts) — таблицы под конкретные задачи: «выручка по дням и каналам», «когорты клиентов». Их и подключают к дашбордам.

```sql
-- Витрина «продажи по дням»: такие таблицы считают по расписанию и читают дашборды
SELECT o.order_date,
       c.city,
       COUNT(*)                                            AS orders,
       COUNT(*) FILTER (WHERE o.status = 'delivered')       AS delivered,
       SUM(o.amount) FILTER (WHERE o.status = 'delivered')  AS revenue
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
GROUP BY o.order_date, c.city
ORDER BY o.order_date DESC, revenue DESC
LIMIT 10;
```

## ETL и ELT

Данные в хранилище попадают процессом:

- **ETL** (Extract — Transform — Load): выгрузить из источника, преобразовать по дороге, загрузить готовое;
- **ELT** (Extract — Load — Transform): сначала загрузить сырьё в хранилище, а преобразовывать уже там, SQL-запросами. Современные хранилища достаточно мощные, поэтому ELT сейчас популярнее: сырьё всегда под рукой, а логика прозрачна.

Загрузки бывают **полными** (каждый раз перезаписать всё) и **инкрементальными** (догрузить только новое и изменившееся). Инкрементальные быстрее, но сложнее: нужно понять, что именно изменилось. Об этом — в теме про ETL и Airflow.

## Кто строит хранилище

Хранилище строят **дата-инженеры**, а модели детального слоя и витрины всё чаще пишут **аналитики-инженеры** (analytics engineers) на SQL с помощью инструментов вроде **dbt**. Аналитику данных важно понимать устройство хранилища: откуда приходят данные, как часто обновляются, какие есть слои и где искать «правильную» таблицу с выручкой.

## Чему верить

В хорошем хранилище у каждой важной таблицы есть:

- **владелец** — кого спрашивать;
- **описание** и определения полей;
- **частота обновления** и время последней загрузки;
- **проверки качества**: нет дублей ключей, нет неожиданных пропусков, итоги сходятся с источником.

Если витрина «Выручка» обновилась вчера в 3 часа ночи, а сегодня утром дашборд показывает падение на 40%, сначала проверь загрузку, а не ищи бизнес-причины. Подробнее — в теме про организацию работы с данными.

## Шпаргалка

| Понятие | Суть |
|---|---|
| DWH | общая аналитическая база из всех источников, с историей |
| OLTP / OLAP | рабочие операции / аналитика |
| сырой слой | данные как есть + время загрузки |
| детальный слой | очищенная связанная модель |
| витрина | готовая таблица под задачу или дашборд |
| ETL / ELT | преобразовать до загрузки / после, в хранилище |
| полная / инкрементальная загрузка | всё заново / только новое и изменённое |
