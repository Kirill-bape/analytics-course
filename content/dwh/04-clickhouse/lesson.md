## Почему ClickHouse такой быстрый

**ClickHouse** — колоночная аналитическая база, созданная в Яндексе для Метрики. Сейчас это одно из самых популярных хранилищ в российских компаниях: она считает агрегаты по миллиардам строк за секунды. Секрет в нескольких идеях:

- **хранение по столбцам**: чтобы посчитать `SUM(amount)`, читается только столбец `amount`, а не целые строки;
- **сжатие**: в столбце однотипные значения, они сжимаются в разы;
- **разреженный индекс** и **сортировка данных на диске**: база быстро пропускает целые блоки, которые не подходят под условие;
- **параллельность**: запрос делится между ядрами процессора и серверами.

Платой за скорость стали ограничения: ClickHouse не любит частые обновления и удаления отдельных строк, а `JOIN` больших таблиц в нём дороже, чем в классических базах. Он создан для **вставки пачками и чтения агрегатов**.

> 🧪 В приложении работает DuckDB — тоже колоночная аналитическая база, очень похожая по духу. Синтаксис ClickHouse, который здесь не запустится, показан серыми блоками.

## Таблица MergeTree

Основной движок таблиц — **MergeTree**. При создании таблицы указывают сортировку и разбиение:

```text
CREATE TABLE orders
(
    order_id     UInt64,
    customer_id  UInt64,
    order_date   Date,
    status       LowCardinality(String),
    amount       Decimal(12, 2)
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(order_date)
ORDER BY (customer_id, order_date);
```

- **`ORDER BY`** — порядок хранения строк и одновременно **первичный ключ**. Запросы с фильтром по первым столбцам ключа (`WHERE customer_id = 1042`) читают очень мало данных. Ключ выбирают под самые частые фильтры.
- **`PARTITION BY`** — разбиение на части, обычно по месяцам. Удобно удалять старые данные целыми партициями и пропускать ненужные месяцы.
- **`LowCardinality(String)`** — тип для столбцов с небольшим числом разных значений (статус, город): хранит их как словарь и экономит место.

> ⚠️ Первичный ключ в ClickHouse **не гарантирует уникальность**. Две строки с одинаковым `order_id` спокойно лежат рядом. Дубли — частая ловушка при загрузке.

## Специальные движки

| Движок | Что делает | Когда нужен |
|---|---|---|
| `ReplacingMergeTree` | при слиянии частей оставляет одну версию строки с тем же ключом | обновляемые данные: статусы заказов |
| `SummingMergeTree` | складывает числовые столбцы строк с одинаковым ключом | счётчики, предагрегаты |
| `AggregatingMergeTree` | хранит промежуточные состояния агрегатов | сложные предагрегации (уникальные, квантили) |

Слияние частей происходит в фоне и **не мгновенно**. Поэтому в `ReplacingMergeTree` до слияния дубли ещё видны. Их убирают в запросе модификатором `FINAL` или функцией `argMax`.

## Полезные функции

ClickHouse славится функциями, которых нет в обычном SQL. Многие есть и в DuckDB под похожими именами:

| ClickHouse | DuckDB | Что делает |
|---|---|---|
| `argMax(x, t)` | `arg_max(x, t)` | значение `x` из строки с максимальным `t` |
| `uniq(x)` | `approx_count_distinct(x)` | приблизительное число уникальных — быстро |
| `uniqExact(x)` | `COUNT(DISTINCT x)` | точное число уникальных — медленнее |
| `quantile(0.9)(x)` | `quantile_cont(x, 0.9)` | 90-й процентиль |
| `countIf(cond)` | `COUNT(*) FILTER (WHERE cond)` | счётчик с условием |
| `toStartOfMonth(d)` | `date_trunc('month', d)` | начало месяца |

```sql
-- Последний заказ каждого клиента без подзапросов: arg_max
SELECT customer_id,
       MAX(order_date)                AS last_date,
       arg_max(amount, order_date)    AS last_amount,
       arg_max(status, order_date)    AS last_status
FROM orders
GROUP BY customer_id
ORDER BY last_date DESC
LIMIT 5;
```

## Материализованные представления

**Материализованное представление** в ClickHouse — триггер на вставку: каждая новая пачка строк сразу агрегируется и дописывается в отдельную таблицу. Так витрины обновляются в реальном времени, без ночных пересчётов:

```text
CREATE MATERIALIZED VIEW mv_daily_sales
ENGINE = SummingMergeTree ORDER BY (order_date, city)
AS SELECT order_date, city, count() AS orders, sum(amount) AS revenue
FROM orders_raw
GROUP BY order_date, city;
```

## Как писать быстрые запросы в ClickHouse

1. Фильтруй по столбцам ключа сортировки и по партиции (дате).
2. Выбирай только нужные столбцы — никаких `SELECT *` по большим таблицам.
3. В `JOIN` справа ставь **маленькую** таблицу: она загружается в память.
4. Для оценок на больших данных используй приблизительные функции (`uniq`, `quantile`) — они в разы быстрее точных.
5. Помни про дубли и фоновые слияния: проверяй уникальность ключей.

## Шпаргалка

| Понятие | Суть |
|---|---|
| колоночное хранение | читаются только нужные столбцы |
| `ORDER BY` в MergeTree | порядок на диске и первичный ключ (не уникальный!) |
| `PARTITION BY` | разбиение, обычно по месяцам |
| `ReplacingMergeTree` | версии строк, дубли до слияния — `FINAL` или `argMax` |
| `argMax` / `arg_max` | значение из строки с максимумом |
| `uniq` vs `uniqExact` | приблизительно и быстро vs точно и медленнее |
| материализованное представление | агрегирует данные в момент вставки |
