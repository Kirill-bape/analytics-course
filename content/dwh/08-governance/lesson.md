## Данных много — доверия мало

В компании сотни таблиц, десятки дашбордов и несколько команд. Типичные жалобы: «в двух отчётах разная выручка», «кто знает, что значит поле `flag_2`?», «вчера витрина не обновилась, а мы приняли решение по старым цифрам». **Управление данными (data governance)** — набор правил и ролей, чтобы данным можно было доверять.

## Качество данных

Качество проверяют по нескольким измерениям:

| Измерение | Вопрос | Пример проверки |
|---|---|---|
| полнота | всё ли заполнено? | доля пустых `city` |
| уникальность | нет ли дублей? | `COUNT(*) = COUNT(DISTINCT order_id)` |
| ссылочная целостность | все ли ссылки ведут на существующие записи? | заказы с несуществующим клиентом |
| корректность | значения в допустимых границах? | сумма > 0, статус из списка |
| согласованность | не противоречат ли поля друг другу? | доставка раньше заказа |
| свежесть | данные актуальны? | последняя дата загрузки = вчера |

Каждую проверку удобно писать как запрос, который считает **число нарушений**: ноль — проверка пройдена. Несколько проверок собирают в один запрос:

```sql
-- Проверки качества таблицы заказов: каждое число должно быть нулём
SELECT COUNT(*) - COUNT(DISTINCT order_id)                                        AS duplicate_ids,
       COUNT(*) FILTER (WHERE amount <= 0)                                        AS bad_amount,
       COUNT(*) FILTER (WHERE delivery_date < order_date)                         AS delivery_before_order,
       COUNT(*) FILTER (WHERE status = 'delivered' AND delivery_date IS NULL)     AS delivered_without_date,
       COUNT(*) FILTER (WHERE customer_id NOT IN (SELECT customer_id FROM customers)) AS unknown_customer
FROM orders;
```

В реальных командах такие проверки автоматизируют: тесты в **dbt** (`unique`, `not_null`, `relationships`), библиотеки **Great Expectations** и **Soda**. Проверки запускаются в конце каждой загрузки в Airflow. Если хоть одна упала, витрина не публикуется, а команда получает уведомление.

> 💡 Ссылочную целостность проверяют через `NOT EXISTS` или `LEFT JOIN … WHERE правая.id IS NULL`. С `NOT IN` осторожно: если в подзапросе встретится `NULL`, условие не вернёт ни одной строки.

## Каталог, словарь и происхождение данных

- **Каталог данных** (DataHub, OpenMetadata, Amundsen) — «поисковик» по таблицам: описание, владелец, частота обновления, примеры запросов.
- **Словарь метрик** — одно утверждённое определение для каждой метрики: что такое «выручка» (с возвратами или без? с НДС?), «активный пользователь», «конверсия». Его часто оформляют как **семантический слой**: метрика описана один раз, и все дашборды берут её оттуда.
- **Происхождение данных (data lineage)** — граф «откуда пришло поле»: из какой системы, через какие преобразования. Он нужен, чтобы понять, какие отчёты сломаются при изменении источника.

## Роли

| Роль | За что отвечает |
|---|---|
| владелец данных (data owner) | решает, кто и как может использовать данные домена |
| стюард данных (data steward) | следит за качеством и описаниями |
| дата-инженер | загрузки, хранилище, инфраструктура |
| аналитик-инженер | модели и витрины в хранилище, dbt, тесты |
| аналитик данных | вопросы бизнеса, отчёты, исследования |

**Контракт данных (data contract)** — договорённость между командой-источником и потребителями: какие поля, типы и гарантии свежести у таблицы. Источник не может молча переименовать столбец и сломать чужие отчёты.

В больших компаниях встречается подход **data mesh**: каждая продуктовая команда сама отвечает за свои данные как за продукт, а общая платформа даёт инструменты.

## Персональные данные

**Персональные данные** — всё, по чему можно определить человека: ФИО, телефон, почта, адрес, дата рождения в сочетании с другими полями. В России их обработку регулирует **закон № 152-ФЗ «О персональных данных»**, и за утечки предусмотрены крупные штрафы.

Правила аналитика:

- брать **только нужные** поля: для анализа оттока не нужны ФИО и телефоны;
- **псевдонимизировать**: заменить идентификатор хешем, чтобы данные нельзя было напрямую связать с человеком;
- **обобщать**: вместо даты рождения — год или возрастная группа, вместо адреса — город;
- не выгружать персональные данные на личный компьютер, в публичные облака и чаты;
- доступы выдаются по ролям и только на нужный срок.

```sql
-- Обезличенная выгрузка: без ФИО, вместо id — хеш, вместо даты рождения — год
SELECT md5(CAST(customer_id AS VARCHAR)) AS client_key,
       year(birth_date)                  AS birth_year,
       city,
       acquisition_channel
FROM customers
LIMIT 5;
```

> ⚠️ Хеш от id — **псевдонимизация**, а не полная анонимизация: зная исходные id, хеш можно пересчитать и восстановить связь. Поэтому такие данные всё равно защищают.

## Шпаргалка

| Понятие | Суть |
|---|---|
| проверка качества | запрос считает нарушения, ноль — пройдено |
| полнота, уникальность, целостность, корректность, согласованность, свежесть | измерения качества |
| каталог данных | описания таблиц, владельцы, поиск |
| словарь метрик / семантический слой | одно определение метрики для всех |
| lineage | откуда пришло поле и что от него зависит |
| контракт данных | гарантии источника перед потребителями |
| 152-ФЗ | закон о персональных данных |
| псевдонимизация | замена идентификаторов хешем |
