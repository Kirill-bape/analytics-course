## Данные должны обновляться сами

Витрина продаж полезна, только если она свежая. Каждую ночь нужно: забрать новые заказы из базы сайта, клиентов из CRM, расходы из рекламных кабинетов, загрузить их в хранилище, пересчитать детальный слой и витрины, проверить качество и только потом открыть дашборды. Делать это руками каждую ночь невозможно — нужен **оркестратор**.

**Apache Airflow** — самый распространённый оркестратор задач с данными. Он запускает шаги по расписанию, в правильном порядке, повторяет упавшие и показывает, что сломалось.

## DAG — граф задач

Процесс в Airflow описывается как **DAG** (directed acyclic graph) — граф задач со стрелками-зависимостями и без циклов:

```text
выгрузить_заказы ─┐
                  ├─> собрать_детальный_слой ─> пересчитать_витрины ─> проверить_качество
выгрузить_клиентов┘
```

DAG пишут на Python:

```py
from datetime import datetime
from airflow import DAG
from airflow.operators.python import PythonOperator

with DAG(
    dag_id="daily_sales",
    start_date=datetime(2026, 1, 1),
    schedule="0 3 * * *",        # каждый день в 03:00
    catchup=False,
) as dag:
    extract_orders = PythonOperator(task_id="extract_orders", python_callable=load_orders)
    extract_clients = PythonOperator(task_id="extract_clients", python_callable=load_clients)
    build_core = PythonOperator(task_id="build_core", python_callable=build_core_layer)
    build_marts = PythonOperator(task_id="build_marts", python_callable=build_marts)

    [extract_orders, extract_clients] >> build_core >> build_marts
```

- **оператор** — тип задачи: запустить Python-функцию, SQL-запрос, bash-команду;
- **`>>`** — зависимость: правая задача стартует после успеха левой;
- **расписание** записывают в формате cron.

| cron | Когда |
|---|---|
| `0 3 * * *` | каждый день в 03:00 |
| `0 * * * *` | каждый час в 00 минут |
| `0 9 * * 1` | по понедельникам в 09:00 |
| `0 0 1 * *` | первого числа каждого месяца в полночь |

Поля cron по порядку: минута, час, день месяца, месяц, день недели.

## Порядок выполнения

Airflow выполняет задачи в **топологическом порядке**: задача стартует, когда готовы все её предшественники; независимые задачи идут параллельно. Тот же порядок умеет считать стандартная библиотека Python:

```python
from graphlib import TopologicalSorter

dag = {
    "build_core": {"extract_orders", "extract_clients"},
    "build_marts": {"build_core"},
    "check_quality": {"build_marts"},
}
print(list(TopologicalSorter(dag).static_order()))
```

## Идемпотентность — главное правило

**Идемпотентная** задача даёт один и тот же результат, сколько раз её ни запусти. Это критично: задачи падают и перезапускаются, а данные за прошлые дни иногда приходится пересчитать (**backfill**).

Неидемпотентно: «добавить в витрину строки за вчера» — второй запуск задвоит данные.

Идемпотентно: «**удалить** из витрины строки за вчера, **затем** вставить их заново» — сколько ни запускай, результат одинаковый.

```sql
-- Идемпотентная загрузка дня в витрину: сначала удаляем, потом вставляем
CREATE TABLE mart AS
SELECT order_date, COUNT(*) AS orders FROM orders WHERE order_date < '2026-06-30' GROUP BY order_date;

DELETE FROM mart WHERE order_date = '2026-06-29';
INSERT INTO mart SELECT order_date, COUNT(*) FROM orders WHERE order_date = '2026-06-29' GROUP BY order_date;

SELECT COUNT(*) AS days, SUM(orders) AS orders FROM mart;
```

Задача Airflow получает **логическую дату запуска** (`{{ ds }}`) и обрабатывает данные именно за неё, а не «за последние 24 часа от текущего момента». Так перезапуск за прошлую дату обработает правильный день.

## Надёжность

- **retries**: задача повторяется N раз с паузой — источник мог быть временно недоступен;
- **сенсоры**: задача ждёт события — файла в папке, готовности другой таблицы;
- **уведомления**: при падении — сообщение в чат команды;
- **проверки качества** в конце DAG: число строк, дубли ключей, пропуски. Если проверка не прошла, витрины не публикуются, а люди не видят неверные цифры.

## Где здесь dbt

Трансформации внутри хранилища часто пишут в **dbt** (data build tool): каждая модель — `SELECT`-запрос в отдельном файле, dbt сам строит порядок по ссылкам между моделями, создаёт таблицы, запускает тесты (уникальность, не-пустота) и генерирует документацию. Airflow запускает dbt как одну из задач. Для аналитика dbt — самый короткий путь к инженерии данных: это просто SQL с хорошими привычками.

## Шпаргалка

| Понятие | Суть |
|---|---|
| DAG | граф задач с зависимостями, без циклов |
| оператор | тип задачи: Python, SQL, bash |
| `a >> b` | b после a |
| cron | минута, час, день, месяц, день недели |
| идемпотентность | повторный запуск даёт тот же результат: удалить → вставить |
| логическая дата | задача обрабатывает свой день, а не «последние сутки» |
| backfill | пересчёт за прошлые даты |
| retries, сенсоры, проверки | надёжность конвейера |
