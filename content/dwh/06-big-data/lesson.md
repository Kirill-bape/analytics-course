## Когда данных слишком много

Пока данные помещаются на одном сервере, хватает PostgreSQL или ClickHouse. Но журнал событий крупного сервиса — это терабайты в день: такой объём не поместится на один диск и не обработается одним процессором за разумное время. Решение — **горизонтальное масштабирование**: взять десятки или сотни обычных машин и раздать каждой свой кусок работы.

Первой массовой системой такого рода был **Hadoop**: файловая система **HDFS** хранила файлы кусками на многих машинах, а модель **MapReduce** обрабатывала их параллельно. Сегодня Hadoop почти вытеснили **Spark** и облачные хранилища, но идеи остались те же.

## MapReduce: раздели и собери

Любой расчёт на кластере устроен в три шага:

1. **map** — каждая машина обрабатывает свой кусок данных и считает **частичный результат**;
2. **shuffle** — частичные результаты пересылаются так, чтобы всё про один ключ оказалось на одной машине;
3. **reduce** — частичные результаты объединяются в итог.

Это можно сымитировать в pandas, разрезав таблицу на куски:

```python
# Делим заказы на 4 «машины»
chunks = [orders.iloc[i:i + 4000] for i in range(0, len(orders), 4000)]
print("строк в кусках:", [len(c) for c in chunks])

# map: каждая машина считает заказы по статусам в своём куске
parts = [c["status"].value_counts() for c in chunks]

# reduce: складываем частичные результаты
total = pd.concat(parts).groupby(level=0).sum()
print(total)
print("совпадает с расчётом целиком:", total.equals(orders["status"].value_counts().sort_index()))
```

> ⚠️ Складывать можно суммы и количества. А вот **среднее средних** — ошибка: куски разного размера, и среднее по маленькому куску получит такой же вес, как по большому. Поэтому на шаге map считают сумму и количество, а среднее — только в конце.

## Apache Spark

**Spark** — главный движок обработки больших данных. Он держит промежуточные данные в памяти и поэтому в десятки раз быстрее старого MapReduce. Аналитику с ним удобно: таблицы в Spark называются **DataFrame** и похожи на pandas, а ещё есть **Spark SQL**.

```py
from pyspark.sql import SparkSession, functions as F

spark = SparkSession.builder.appName("sales").getOrCreate()
orders = spark.read.parquet("s3://shop-dwh/orders/")

daily = (orders
         .filter(F.col("status") == "delivered")
         .groupBy("order_date")
         .agg(F.sum("amount").alias("revenue")))

daily.show(5)      # только здесь Spark начинает считать

# то же самое на SQL
orders.createOrReplaceTempView("orders")
spark.sql("SELECT order_date, SUM(amount) FROM orders GROUP BY order_date").show(5)
```

Три идеи, без которых Spark непонятен:

- **ленивые вычисления**: `filter`, `groupBy`, `select` (**трансформации**) только записывают план. Вычисление запускают **действия**: `show`, `count`, `collect`, `write`. Spark видит весь план целиком и оптимизирует его;
- **партиции**: данные делятся на куски (обычно около 128 МБ), каждый кусок — отдельная задача для ядра процессора;
- **shuffle** — пересылка данных между машинами при `groupBy`, `join`, `orderBy`. Это самая дорогая операция. Если маленький справочник соединяют с огромной таблицей, его рассылают целиком на все машины (**broadcast join**), и shuffle не нужен.

## Где лежат данные: S3 и форматы файлов

Сейчас большие данные чаще всего хранят в **объектном хранилище** — Amazon S3 или совместимых с ним (Yandex Object Storage, VK Cloud, MinIO). Это бесконечная и дешёвая «папка» с файлами по адресам вида `s3://бакет/путь/файл.parquet`.

Формат файлов важен не меньше, чем движок:

| Формат | Как хранит | Когда |
|---|---|---|
| CSV | текст по строкам, без типов | обмен с людьми и Excel |
| JSON | текст, вложенные структуры | ответы API, логи |
| **Parquet** | **по столбцам**, с типами, сжатием и статистикой min/max | аналитика — стандарт де-факто |
| ORC | по столбцам, похож на Parquet | экосистема Hadoop/Hive |
| Avro | по строкам, со схемой | потоки событий, Kafka |

Parquet хорош для аналитики по тем же причинам, что и ClickHouse: запрос `SUM(amount)` читает только один столбец, данные сжаты в разы, а по статистике min/max движок пропускает куски файла, где точно нет нужных строк.

Таблицы раскладывают по **папкам-партициям**:

```text
s3://shop-dwh/orders/month=2026-04/part-0001.parquet
s3://shop-dwh/orders/month=2026-05/part-0001.parquet
s3://shop-dwh/orders/month=2026-06/part-0001.parquet
```

Запрос с фильтром по месяцу читает только нужные папки — это называется **partition pruning**. Посмотрим, какие партиции получились бы у наших заказов:

```sql
-- Партиции по месяцам: сколько строк лежало бы в каждой папке
SELECT strftime(order_date, '%Y-%m') AS partition_month, COUNT(*) AS rows_in_partition
FROM orders
GROUP BY partition_month
ORDER BY partition_month DESC
LIMIT 6;
```

> 🧪 DuckDB умеет читать Parquet прямо из S3: `SELECT … FROM 's3://shop-dwh/orders/*/*.parquet'`. Так многие аналитики разбирают большие выгрузки на своём ноутбуке без всякого кластера.

## Lakehouse: озеро + хранилище

- **Озеро данных (data lake)** — файлы в S3: дёшево, любые форматы, но нет транзакций, обновлений и порядка. Без дисциплины озеро превращается в «болото».
- **Хранилище (DWH)** — порядок, SQL, транзакции, но дороже и менее гибко.
- **Lakehouse** объединяет их: файлы Parquet лежат в S3, а поверх них **табличный формат** — **Apache Iceberg**, **Delta Lake** или **Apache Hudi** — добавляет транзакции, `UPDATE` и `DELETE`, историю версий («путешествие во времени»: запрос к таблице какой она была вчера) и изменение схемы. Читать такие таблицы умеют Spark, Trino, ClickHouse и DuckDB.

## Потоки событий

Не все данные приходят раз в сутки. Клики, платежи и показы рекламы идут непрерывным **потоком**. Их собирает брокер сообщений **Apache Kafka** — очередь, в которую сервисы пишут события, а потребители читают их. Обработкой потока занимаются Spark Structured Streaming и Apache Flink, а ClickHouse умеет читать Kafka сам. Аналитик обычно видит результат — таблицы, которые обновляются каждые несколько секунд или минут.

## Шпаргалка

| Понятие | Суть |
|---|---|
| map → shuffle → reduce | частичные результаты на машинах → пересылка по ключу → объединение |
| среднее на кластере | сумма и количество по кускам, деление в конце |
| Spark | движок больших данных: DataFrame и SQL |
| трансформации и действия | план строится лениво, считается при `show`/`count`/`write` |
| shuffle | пересылка между машинами — самая дорогая операция |
| S3 | объектное хранилище файлов |
| Parquet | колоночный сжатый формат со статистикой |
| partition pruning | чтение только нужных папок-партиций |
| Lakehouse | файлы в S3 + Iceberg/Delta: транзакции и версии |
| Kafka | очередь событий для потоковых данных |
