## Зачем ещё одна модель

Звезда удобна для отчётов, но её трудно менять: появился новый источник клиентов — и нужно перестраивать измерение «Клиент» и все загрузки. В крупных хранилищах, где источников десятки и они постоянно меняются, для детального слоя используют модели, рассчитанные на **гибкость и полную историю**. Самые известные — **Data Vault** и **Anchor Modeling**.

## Data Vault: хабы, линки, сателлиты

В Data Vault всего три типа таблиц:

| Тип | Что хранит | Пример |
|---|---|---|
| **хаб** (hub) | только бизнес-ключи сущности: то, по чему её узнают | `hub_customer`: номер клиента |
| **линк** (link) | связи между хабами | `link_order_customer`: какой клиент сделал заказ |
| **сателлит** (satellite) | описательные атрибуты с историей | `sat_customer`: город, канал, дата регистрации |

У каждой строки есть служебные поля:

- **хеш-ключ** — хеш бизнес-ключа (например, `md5` от номера клиента). Его можно посчитать в любом источнике независимо, поэтому загрузки идут параллельно;
- **load_date** — когда строка загружена;
- **record_source** — из какой системы пришла.

```sql
-- Хаб клиентов: только ключ и служебные поля
SELECT md5(CAST(customer_id AS VARCHAR)) AS customer_hk,
       customer_id,
       TIMESTAMP '2026-07-01 03:00:00'   AS load_date,
       'crm'                             AS record_source
FROM customers
LIMIT 3;
```

**Сателлиты хранят историю**: при изменении атрибутов добавляется новая строка с новым `load_date`, старая не трогается. Чтобы не плодить одинаковые строки, сравнивают **хеш атрибутов** (hash diff): если он не изменился, новую версию не пишут.

## Плюсы и минусы

Плюсы:

- **новый источник — новые сателлиты**, существующие таблицы не меняются;
- **полная история** и аудит: видно, когда и откуда пришло каждое значение;
- **параллельная загрузка** хабов, линков и сателлитов.

Минусы:

- **много таблиц и `JOIN`**: прямо по Data Vault отчёты писать неудобно и медленно;
- нужна дисциплина и автоматизация (генераторы загрузок).

Поэтому Data Vault — это **детальный слой**, а для аналитиков и BI поверх него строят звёзды и витрины. Если ты пришёл в компанию и видишь таблицы `hub_…`, `link_…`, `sat_…`, — это оно; отчёты ищи в слое витрин.

## Anchor Modeling

**Anchor Modeling** идёт ещё дальше: почти **6-я нормальная форма**, где каждый атрибут — отдельная таблица.

| Элемент | Аналог в Data Vault | Пример |
|---|---|---|
| **якорь** (anchor) | хаб | клиент |
| **атрибут** (attribute) | один атрибут сателлита | город клиента — своя таблица с историей |
| **связь** (tie) | линк | клиент — заказ |
| **узел** (knot) | справочник значений | список статусов |

Добавить атрибут — значит добавить таблицу, ничего не перестраивая. Цена — огромное число таблиц и запросы, которые без автоматических представлений не написать руками. Такой подход используют, например, в крупных российских компаниях с колоночными хранилищами.

## Как собрать витрину из Data Vault

Логика всегда одна: от хаба через линки к нужным сателлитам, из сателлита берём **актуальную** версию (с максимальным `load_date`) или версию на нужную дату:

```sql
-- Схема запроса (по нашим таблицам, без настоящего Data Vault):
-- hub_customer → link_order_customer → hub_order → sat_order (статус, сумма)
--              → sat_customer (последняя версия: город)
SELECT c.city, COUNT(*) AS orders
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
GROUP BY c.city
ORDER BY orders DESC
LIMIT 3;
```

## Шпаргалка

| Понятие | Суть |
|---|---|
| хаб | бизнес-ключи сущности + хеш-ключ + время загрузки + источник |
| линк | связь между хабами |
| сателлит | атрибуты с историей, новая строка при изменении |
| hash diff | хеш атрибутов, чтобы не писать одинаковые версии |
| Anchor | якорь, атрибут (отдельная таблица), связь, узел |
| где используют | детальный слой; отчёты — в витринах поверх |
