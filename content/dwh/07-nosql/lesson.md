## Не только таблицы

Реляционные базы (PostgreSQL, MySQL) хранят данные в таблицах со строгой схемой и связями. Это надёжно, но не всегда удобно: у товаров интернет-магазина разные наборы характеристик, сессия пользователя должна читаться за миллисекунду, а миллиард сообщений в чатах нужно писать без остановки. Для таких задач придумали **NoSQL**-базы — «не только SQL».

| Тип | Пример | Как хранит | Где применяют |
|---|---|---|---|
| документная | **MongoDB** | документы JSON с вложенными полями | каталоги, профили, контент |
| ключ — значение | **Redis** | значение по ключу, в оперативной памяти | кэш, сессии, счётчики, очереди |
| широкие столбцы | **Cassandra**, HBase | строки по ключу партиции, разбросанные по кластеру | огромные потоки записей: сообщения, события, IoT |
| графовая | **Neo4j** | вершины и рёбра | соцсети, рекомендации, антифрод |
| векторная | Qdrant, pgvector | числовые векторы | поиск похожего, нейросети |

Аналитик редко пишет в NoSQL-базы, но постоянно получает из них данные, поэтому важно понимать их устройство.

## MongoDB: документы

В MongoDB вместо строк — **документы**, похожие на словари Python. В одном документе могут быть вложенные объекты и списки, а у разных документов одной коллекции — разные поля:

```text
{
  "_id": 10457,
  "customer": {"id": 1042, "city": "Казань"},
  "status": "delivered",
  "items": [
    {"sku": "A1", "qty": 2, "price": 990},
    {"sku": "B7", "qty": 1, "price": 4990}
  ]
}
```

Запросы пишут не на SQL, а объектами:

| SQL | MongoDB |
|---|---|
| `SELECT * FROM orders WHERE status = 'delivered'` | `db.orders.find({status: "delivered"})` |
| `… WHERE amount > 5000` | `db.orders.find({amount: {$gt: 5000}})` |
| `GROUP BY` | `db.orders.aggregate([{$group: {_id: "$status", n: {$sum: 1}}}])` |
| развернуть список в строки | стадия `$unwind` |

Гибкая схема — и плюс, и ловушка. Поле может отсутствовать, называться по-разному в старых и новых документах или менять тип. Поэтому при разборе выгрузки из MongoDB обращаются к полям через `.get()`:

```python
users = [
    {"_id": 1, "name": "Анна", "phone": "+7 900 000-00-01"},
    {"_id": 2, "name": "Олег", "email": "oleg@example.com"},
    {"_id": 3, "name": "Ирина", "phone": "+7 900 000-00-03", "email": "ira@example.com"},
    {"_id": 4, "name": "Пётр"},
]
for u in users:
    print(u["name"], "| телефон:", u.get("phone", "—"), "| почта:", u.get("email", "—"))
```

Вложенные списки в аналитике разворачивают в строки — это аналог `$unwind`. В pandas для этого есть `explode`:

```python
docs = pd.DataFrame([
    {"order_id": 1, "tags": ["подарок", "срочно"]},
    {"order_id": 2, "tags": ["срочно"]},
    {"order_id": 3, "tags": []},
])
flat = docs.explode("tags")
print(flat)
print(flat["tags"].value_counts())
```

Списки умеет хранить и DuckDB: функция `list()` собирает значения группы в список, а `len()` считает его длину.

```sql
-- Заказ как документ: список товаров внутри одной строки
SELECT order_id, list(product_id ORDER BY product_id) AS products
FROM order_items
GROUP BY order_id
ORDER BY order_id
LIMIT 5;
```

## Redis: всё в памяти

**Redis** хранит пары «ключ — значение» в оперативной памяти и отвечает за доли миллисекунды. Значением может быть строка, число, список, множество или **отсортированное множество**.

```text
SET session:8f2a "user_id=1042"   EX 3600   -- сессия живёт час
INCR views:product:57                       -- счётчик просмотров +1
ZINCRBY leaderboard 150 "player:12"         -- рейтинг игроков
```

Типичные задачи: **кэш** (запомнить ответ тяжёлого запроса), сессии, счётчики, лимиты запросов, очереди задач, рейтинги. Хранить в Redis историю для отчётов неудобно: он держит данные в памяти, а сложные запросы не поддерживает.

## Cassandra: запись без остановки

**Cassandra** раскладывает данные по многим серверам по **ключу партиции** и выдерживает огромный поток записей. Таблицы проектируют **под конкретный запрос**: если нужно «сообщения чата по времени», ключ партиции — `chat_id`, а сортировка внутри — по `sent_at`. Запрос, не попадающий в ключ («все сообщения со словом "скидка"»), Cassandra выполнить эффективно не может — такие данные выгружают в хранилище и анализируют там.

## Теорема CAP

Распределённая база состоит из многих серверов, и связь между ними иногда рвётся. **Теорема CAP** говорит: при разрыве сети (**P**artition) система должна выбрать одно из двух:

- **C**onsistency, согласованность: все видят одинаковые, самые свежие данные. Если гарантировать это нельзя, система отказывает в ответе;
- **A**vailability, доступность: система отвечает всегда, но ответ может быть устаревшим.

Банковский баланс требует согласованности: лучше отказать, чем показать неверную сумму. Счётчик лайков или лента новостей выбирает доступность: не страшно, если лайк появится через секунду.

## Как выбрать базу

- деньги, заказы, связи между сущностями, строгие правила → **PostgreSQL**;
- аналитика по миллиардам строк → **ClickHouse** или другое колоночное хранилище;
- разнородные документы, быстрое развитие продукта → **MongoDB**;
- скорость, кэш, счётчики → **Redis**;
- огромный поток записей по ключу → **Cassandra**;
- связи «друзья друзей», маршруты → **Neo4j**.

В реальной компании живут все сразу, а данные из них собираются в одно хранилище для анализа.

## Шпаргалка

| Понятие | Суть |
|---|---|
| документ | JSON с вложенными полями, схема у каждого своя |
| `.get(поле, по_умолчанию)` | безопасное чтение поля, которого может не быть |
| `$unwind` / `explode` / `unnest` | развернуть список в строки |
| Redis | ключ — значение в памяти: кэш, сессии, счётчики |
| Cassandra | ключ партиции, таблица под запрос |
| CAP | при разрыве сети — согласованность или доступность |
