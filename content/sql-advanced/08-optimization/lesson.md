## Когда запрос тормозит

На учебной базе любой запрос отвечает за долю секунды. В компании таблица заказов может весить сотни гигабайт, и плохо написанный запрос будет считаться полчаса или упадёт. Чаще всего виноваты три вещи:

- база читает **всю таблицу**, хотя нужна маленькая часть строк;
- запрос тащит **лишние столбцы** и лишние строки через несколько `JOIN`;
- одна и та же сложная логика **копируется** из запроса в запрос, и где-то в копии появляется ошибка.

В этой теме разберём три инструмента: представления, индексы и план запроса. И правила, которые делают запросы быстрее в любой базе.

> 🧪 В этой теме команды `CREATE VIEW` и `CREATE INDEX` выполняются в песочнице: после запуска всё отменяется. Поэтому пиши сценарий целиком: создать → использовать.

## Представление (VIEW): сохранённый запрос

**Представление** — это запрос, которому дали имя. Обращаться к нему можно как к таблице, но данных оно не хранит: при каждом обращении база выполняет запрос заново.

```sql
CREATE VIEW delivered_orders AS
SELECT order_id, customer_id, order_date, amount
FROM orders
WHERE status = 'delivered';

SELECT COUNT(*) AS orders_cnt, SUM(amount) AS revenue
FROM delivered_orders;
```

Зачем это нужно:

- **одно определение на всех.** Правило «выручка — это только доставленные заказы» записано в одном месте. Все отчёты берут данные из `delivered_orders` и считают одинаково;
- **короче запросы.** Сложные `JOIN` и фильтры спрятаны внутри представления;
- **доступы.** Можно дать коллегам доступ к представлению без личных данных клиентов, а не ко всей таблице.

## Представление, таблица или CTE?

| Инструмент | Что хранит | Когда использовать |
|---|---|---|
| CTE (`WITH`) | ничего, живёт только внутри одного запроса | разбить сложный запрос на шаги |
| представление (`CREATE VIEW`) | текст запроса | одна и та же логика нужна во многих запросах и отчётах |
| таблица из запроса (`CREATE TABLE … AS`) | готовые данные на момент создания | расчёт тяжёлый, а результат нужен часто; данные можно обновлять по расписанию |

В PostgreSQL есть ещё **материализованное представление** (`CREATE MATERIALIZED VIEW`). Оно хранит результат, как таблица, и обновляется командой `REFRESH MATERIALIZED VIEW`. Так делают тяжёлые витрины для дашбордов: запрос считается раз в ночь, а дашборд читает готовый результат за секунду.

> ⚠️ Представление не ускоряет запрос само по себе: внутри всё равно выполняется тот же `SELECT`. Оно экономит время **людей**, а не базы.

## Индекс: оглавление для таблицы

Чтобы найти в книге главу про `JOIN`, мы открываем оглавление, а не листаем все страницы. **Индекс** — такое же оглавление для столбца. Без него база ищет строки полным перебором (это называется *seq scan*, последовательный просмотр). С индексом она сразу находит нужные строки.

```sql
CREATE INDEX idx_orders_customer ON orders (customer_id);

SELECT order_id, order_date, amount
FROM orders
WHERE customer_id = 1042
ORDER BY order_date;
```

Индекс помогает, когда запрос выбирает **небольшую часть** строк:

- поиск по точному значению: `WHERE customer_id = 1042`;
- узкий диапазон: `WHERE order_date >= '2026-03-01' AND order_date < '2026-03-02'`;
- соединение по ключу: `JOIN customers c ON c.customer_id = o.customer_id`.

Индекс почти не помогает, когда:

- таблица маленькая: прочитать её целиком быстрее;
- условие подходит под большую часть строк: `WHERE status <> 'cancelled'` всё равно выберет почти всё;
- столбец **завёрнут в функцию**: `WHERE EXTRACT(YEAR FROM order_date) = 2026`. Индекс построен по самим датам, а не по годам, и база не сможет им воспользоваться. Пиши диапазоном: `order_date >= '2026-01-01' AND order_date < '2027-01-01'`.

У индекса есть цена: он занимает место и замедляет `INSERT` и `UPDATE`, ведь при каждой записи база обновляет и оглавление. Поэтому индексы создают не на всё подряд, а на столбцы, по которым часто ищут и соединяют. Обычно это делают инженеры данных, но аналитик должен понимать, почему один запрос летает, а похожий ползёт.

## План запроса: EXPLAIN

Перед выполнением база составляет **план**: в каком порядке читать таблицы, как их соединять, где фильтровать. Посмотреть план можно, поставив перед запросом слово `EXPLAIN`:

```sql
EXPLAIN
SELECT c.city, SUM(o.amount) AS revenue
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
WHERE o.status = 'delivered'
GROUP BY c.city;
```

План читают **снизу вверх**: сначала чтение таблиц (`SEQ_SCAN`) и фильтр, потом соединение (`HASH_JOIN`), потом группировка (`HASH_GROUP_BY`). У каждого шага указано примерное число строк. Если после соединения строк стало в разы больше, чем ожидалось, ищи ошибку в условии `JOIN`.

В PostgreSQL удобнее `EXPLAIN ANALYZE`: запрос выполняется по-настоящему, и для каждого шага видно реальное время. Что искать в плане:

| В плане | Что это значит |
|---|---|
| `Seq Scan` по большой таблице | читается вся таблица; возможно, не хватает индекса или условие мешает индексу |
| `Index Scan` | база пошла по индексу, всё хорошо |
| огромное число строк после `JOIN` | соединение размножило строки: проверь ключи |
| `Sort` на миллионах строк | дорогая сортировка; нужна ли она вообще? |

## Колоночные базы: каждый столбец на счету

Аналитические базы (ClickHouse, DuckDB, BigQuery, Vertica) хранят данные **по столбцам**. Чтобы посчитать `SUM(amount)`, они читают с диска только столбец `amount`. Отсюда главное правило: **`SELECT *` в больших таблицах дорог**. Запрос со звёздочкой читает все столбцы, даже если нужны два. Во многих компаниях за прочитанные гигабайты платят деньги: так устроен, например, BigQuery.

## Правила быстрых запросов

1. **Выбирай только нужные столбцы.** `SELECT order_id, amount` вместо `SELECT *`.
2. **Фильтруй как можно раньше.** Сначала отбери строки за нужный период, потом соединяй.
3. **Не заворачивай столбец в функцию в `WHERE`.** Сравнивай дату с диапазоном.
4. **Агрегируй до `JOIN`.** Если нужна выручка по клиентам с их городом, сначала посчитай выручку в CTE по `orders`, а потом присоедини `customers`. Соединять тысячи строк быстрее, чем миллионы.
5. **Избегай подзапросов, которые выполняются для каждой строки.** Подзапрос вида `(SELECT AVG(price) FROM products p2 WHERE p2.category = p.category)` считает среднее заново для каждого товара. Посчитай средние один раз в CTE и присоедини их.
6. **Исследуй с `LIMIT`.** Чтобы посмотреть, как выглядят данные, хватит `LIMIT 100`.
7. **Проверяй число строк после `JOIN`.** Резкий рост — признак размножения строк, а значит неверного результата и медленного запроса.

```sql
-- Агрегируем до JOIN: сначала выручка по клиентам, потом их город
WITH customer_revenue AS (
    SELECT customer_id, SUM(amount) AS revenue
    FROM orders
    WHERE status = 'delivered'
    GROUP BY customer_id
)
SELECT c.city, SUM(cr.revenue) AS revenue
FROM customer_revenue cr
JOIN customers c ON c.customer_id = cr.customer_id
GROUP BY c.city
ORDER BY revenue DESC
LIMIT 5;
```

## Шпаргалка

| Задача | Как написать |
|---|---|
| сохранить запрос под именем | `CREATE VIEW v AS SELECT …` |
| удалить представление | `DROP VIEW v` |
| сохранить готовый результат | `CREATE TABLE t AS SELECT …` |
| создать индекс | `CREATE INDEX idx_name ON t (column)` |
| посмотреть план | `EXPLAIN SELECT …` |
| план с реальным временем (PostgreSQL) | `EXPLAIN ANALYZE SELECT …` |
| фильтр по месяцу без функции | `d >= '2026-03-01' AND d < '2026-04-01'` |
