## Что такое база данных на самом деле

Ты уже семь тем пишешь запросы к нашей базе. Пора заглянуть под капот: как она устроена и почему устроена именно так.

**База данных** — это набор таблиц, которые знают друг о друге. У каждой таблицы:

- **имя** — `orders`, `customers`, `products`;
- **столбцы** с именем и **типом данных**: в `order_date` могут лежать только даты, в `amount` — только числа;
- **строки** — сами записи: один заказ, один покупатель, один товар.

Главное отличие от листа Excel: в Excel в любую ячейку можно вписать что угодно, а база **следит за порядком**. В столбец с датами не получится записать «вчера», а в столбец с ценой — «дорого». Благодаря этому аналитик может доверять данным и не проверять каждую ячейку вручную.

## Схема: из каких таблиц состоит база

Описание всех таблиц, их столбцов и связей называется **схемой базы**. Её можно посмотреть на вкладке «Схема данных» внизу экрана, а можно спросить у самой базы.

Список таблиц:

```sql
SHOW TABLES;
```

Столбцы одной таблицы и их типы:

```sql
DESCRIBE orders;
```

Тот же список лежит в служебной таблице `information_schema.columns`. Её можно фильтровать и сортировать как любую другую. Это удобно, когда таблиц десятки, а нужно найти, например, все столбцы со словом `date`:

```sql
SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE column_name LIKE '%date%'
ORDER BY table_name, ordinal_position;
```

`ordinal_position` — номер столбца в таблице (1, 2, 3, …). По нему сортируют, чтобы столбцы шли в том же порядке, что и в самой таблице.

> 💡 На новой работе первым делом изучают схему: какие есть таблицы, что в них лежит и как они связаны. `information_schema` есть почти во всех базах: PostgreSQL, MySQL, ClickHouse, DuckDB.

## Ключи: как таблицы ссылаются друг на друга

Посмотри на заказ: в нём нет имени и города покупателя, только `customer_id`. Почему бы не записать всё в одну таблицу?

Представь, что покупатель сделал 30 заказов и переехал из Казани в Самару. Если город хранится в каждом заказе, его придётся исправить в 30 местах, а где-нибудь обязательно забудут. Поэтому данные раскладывают по разным таблицам: **каждый факт хранится один раз**, а таблицы ссылаются друг на друга по номерам. Такое устройство называют **нормализацией**.

Для ссылок нужны ключи.

**Первичный ключ** (primary key) — столбец, который однозначно определяет строку. Два правила: значения **не повторяются** и **не бывают пустыми**.

| Таблица | Первичный ключ |
|---|---|
| `customers` | `customer_id` |
| `products` | `product_id` |
| `orders` | `order_id` |
| `order_items` | `item_id` |

**Внешний ключ** (foreign key) — столбец, который хранит первичный ключ **другой** таблицы, то есть ссылается на неё:

| Столбец | Ссылается на |
|---|---|
| `orders.customer_id` | `customers.customer_id` — кто сделал заказ |
| `order_items.order_id` | `orders.order_id` — в каком заказе позиция |
| `order_items.product_id` | `products.product_id` — какой товар купили |

Связь «покупатель → заказы» называется **«один ко многим»**: у одного покупателя может быть много заказов, но у каждого заказа ровно один покупатель. Поэтому в `orders` значения `customer_id` повторяются, и это нормально.

Проверить, что столбец годится в первичные ключи, можно через `COUNT`: если разных значений столько же, сколько строк, то повторов нет.

```sql
SELECT COUNT(*)                 AS rows_cnt,
       COUNT(DISTINCT order_id) AS unique_ids
FROM orders;
```

> 💡 Соединять таблицы по ключам мы научимся в модуле «Продвинутый SQL» (оператор `JOIN`). Именно ради этого ключи и нужны.

## Типы данных

У каждого столбца есть тип. Он определяет, что в столбце может лежать и что с этим можно делать.

| Тип | Что хранит | Пример из нашей базы |
|---|---|---|
| `INTEGER` | целые числа | `order_id`, `quantity` |
| `DECIMAL(12,2)` | точные дробные числа: всего до 12 цифр, из них 2 после запятой | `price`, `amount` |
| `DOUBLE` | дробные числа «примерно» (с крошечной погрешностью) | результат `AVG` |
| `VARCHAR` | текст любой длины | `city`, `status` |
| `DATE` | дата без времени | `order_date` |
| `TIMESTAMP` | дата и время | `2026-03-15 18:30:00` |
| `BOOLEAN` | да или нет: `true` / `false` | результат сравнения `price > 1000` |

Узнать тип любого значения или выражения помогает функция `typeof`:

```sql
SELECT typeof(order_id)                AS id_type,
       typeof(amount)                  AS amount_type,
       typeof(order_date)              AS date_type,
       typeof(amount > 1000)           AS compare_type,
       typeof(delivery_date - order_date) AS days_type
FROM orders
LIMIT 1;
```

> ⚠️ Деньги хранят в `DECIMAL`, а не в `DOUBLE`. `DOUBLE` считает с крошечной погрешностью: на миллионах строк копейки «разъезжаются», и отчёт не сходится с бухгалтерией.

## Почему тип важен: текст — не число

Текст сравнивается **по буквам слева направо**, как слова в словаре. Поэтому строка `'10'` «меньше» строки `'9'`: первый символ `1` идёт раньше `9`.

```sql
SELECT '10' < '9' AS as_text,
       10 < 9     AS as_numbers;
```

Если номера или суммы случайно хранятся текстом, сортировка выдаст `1, 10, 100, 2, 25, 3` вместо `1, 2, 3, 10, 25, 100`. Это одна из самых частых ловушек в чужих данных, особенно выгруженных из Excel.

## Превращаем один тип в другой: CAST

`CAST(значение AS тип)` меняет тип значения. Есть короткая запись: `значение::тип`.

```sql
SELECT CAST('2026-03-15' AS DATE) + 10 AS in_ten_days,
       '42'::INTEGER * 2               AS number_from_text,
       CAST(order_id AS VARCHAR)       AS id_as_text
FROM orders
LIMIT 1;
```

Дату тоже можно превратить в текст и взять из неё кусок. Например, первые 7 символов `2026-03-15` — это месяц `2026-03`:

```sql
SELECT order_date,
       LEFT(CAST(order_date AS VARCHAR), 7) AS month
FROM orders
LIMIT 3;
```

Если текст нельзя превратить в нужный тип, база выдаст ошибку:

```sql
-- ⛔ Этот запрос нарочно с ошибкой: запусти и посмотри, что ответит база
SELECT CAST('много' AS INTEGER);
```

Чтобы вместо ошибки получить пустое значение `NULL`, есть `TRY_CAST`. Это удобно, когда в «грязном» столбце попадаются случайные слова:

```sql
SELECT TRY_CAST('много' AS INTEGER) AS bad,
       TRY_CAST('15' AS INTEGER)    AS good;
```

## Ловушка: CAST округляет, а не отбрасывает

При превращении дробного числа в целое `CAST` **округляет по правилам математики**, а не просто отрезает дробную часть:

```sql
SELECT CAST(4.3 AS INTEGER) AS a,
       CAST(4.7 AS INTEGER) AS b,
       FLOOR(4.7)           AS floor_down,
       CEIL(4.3)            AS ceil_up;
```

- `FLOOR` округляет **вниз** до целого: 4.7 → 4;
- `CEIL` округляет **вверх** до целого: 4.3 → 5;
- `ROUND` и `CAST` округляют до ближайшего: 4.7 → 5, 4.3 → 4.

Когда нужен «полный» результат (полных лет, полных звёзд, полных коробок), бери `FLOOR`.

## Шпаргалка

| Задача | Как написать |
|---|---|
| список таблиц | `SHOW TABLES` |
| столбцы таблицы | `DESCRIBE orders` |
| столбцы с фильтром | `SELECT … FROM information_schema.columns WHERE table_name = 'orders'` |
| тип выражения | `typeof(amount)` |
| проверить уникальность | `COUNT(*)` против `COUNT(DISTINCT id)` |
| сменить тип | `CAST(x AS INTEGER)` или `x::INTEGER` |
| без ошибки на мусоре | `TRY_CAST(x AS INTEGER)` → `NULL` |
| округлить вниз / вверх | `FLOOR(x)` / `CEIL(x)` |
